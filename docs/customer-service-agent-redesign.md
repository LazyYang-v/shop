# 集成客服与 Agent 改造记录

日期：2026-10-25。状态：六职责平台、多轮咨询/服务申请进度、订单与客服入口闭环、淘小蜜三栏工作台及 P3 体验精修已实施并提交（截至 `d382858`）；这些功能仍是**后续开发范围，尚未纳入 #9 对 `941fe4e` 的 13 项作品集发布验收**。此前记录的客服完整浏览器回归 70 项通过（46.7 秒），包含 11 项精修专项；前期全量后端 512 项通过、1 项跳过。迁移 `0022` 已应用至 `shop_dev`，API 镜像已在前期更新；P3 只修改前端、测试与文档。P3 真实运行验证使用已有数据，覆盖商城登录、订单摘要、商品重复结果折叠、偏好/通知独立面板及移动抽屉；人工状态与写入交互使用合成浏览器接口验证，未在本轮创建真实工单或留言。真实退款打款、开票、补发、承运商实时轨迹和外部平台接入仍未接通。各层验证分别记录，不相互替代。

## 目标

客服从商城页面进入，沿用当前 `shop_session` 对应的买家身份和权限。访客可使用公开的商品咨询；登录买家无需再次输入密码即可查询本人订单。客服按任务选择商品、订单物流、售后和投诉等专属角色；需要人工处理时创建可跟进的工单，并携带经过裁剪的对话上下文。

当前客服隔离演示使用独立 API、独立数据库和两名固定买家，因此无法验证或复用商城开发库里的会话和订单。商城 API 的身份认证存储则通过 `shop_session`、会话表和当前买家 ID 约束订单访问。复制账号、同步密码或仅靠邮箱映射都不能令隔离演示库里的客服读取商城订单；集成客服必须调用商城权威 API/数据库会话，而不是把商城账号复制到演示库。

## 认证与页面集成（第一阶段）

- 商城后端签发的有效会话是唯一身份来源。客服页面读取当前登录状态；它不采集、不校验第二份密码。
- 客服由商城站点提供，并向同一个商城 API 发请求；登录、登出、会话过期、CSRF 和同源校验都沿用商城实现。
- 未登录访客可以继续使用明确允许的公开商品能力。需要买家权限时，引导打开商城现有登录界面；登录后回到原客服会话入口，不另做客服登录。
- 订单和已保存物流每次请求都以有效会话解析出的买家 ID 查询。只检查角色和订单归属，不依赖固定客服白名单、邮箱、手机号或买家传入的身份字段。
- 隔离演示 `18011` 保持为隔离作品集运行环境时，明确显示它不继承商城登录态；集成客服的开发入口必须与商城 API 共用身份数据。不得把两个数据库接成临时跨库查询。

推荐用户路径：

```text
商城页面 ──联系客服──> 同站点客服
                         │
                         ├─ 有效商城会话 ─> 本人订单与允许的客服工具
                         └─ 匿名会话 ─────> 公开商品/常见问题
                                             │
                                      需要买家权限时
                                             └─ 商城登录后返回客服
```

## Agent 职责

按六个职责建模：入口路由、售前、订单/物流、售后、投诉安抚、人工交接。意图识别覆盖售前商品、订单状态、物流、退换/退款、活动/优惠、投诉/情绪、其他/不确定。情绪作为路由上下文，不授权 Agent 越权或改变业务事实。六职责已实施：入口路由为确定性状态机（`classify`），各角色有版本化 Prompt 定义与工具白名单，编排层按路由结果选择知识答复、固定流程卡、专属 Agent 分支或人工交接。

| 角色 | 职责 | 可调用能力与答复边界 |
|---|---|---|
| 入口路由 | 为每轮咨询识别意图、情绪和置信程度；将 FAQ 交给受控知识答复，将已知业务问题交给固定流程，将开放问题交给一位专属 Agent。 | 低置信、连续两次用户明确标记错误、明确要求人工、投诉或强烈负面情绪时，停止反复猜测并按人工交接规则处理。路由结果须可评测；不由自由生成文本决定工具权限。 |
| 售前 Agent | 商品参数、规格、材质等问答，明确商品对比，基于用户自愿提供的场景/偏好推荐，尺码建议。 | 商品事实来自在售目录或经核实的结构化属性；没有肤质、成分、尺码或活动数据时先追问或说明无依据。推荐不得声称商城背书。 |
| 订单/物流 Agent | 查本人订单状态及商城已保存物流；解释模拟支付和商城当前可执行状态；查询已登记服务申请的审核进度。 | 发货、确认收货及工单回复已接站内通知；承运商异常事件与实时轨迹尚未接通。订单必须明确选择，选择过期后重选；进度查询只读现有工单，不新建申请，不将工单审结解释为业务执行。 |
| 售后 Agent | 按有效政策解释退换货范围和流程，信息不足时追问；展示服务申请、人工工单与申请进度。 | 退款、补偿、补发、质保和退换货当前可登记并人工审核，业务执行系统尚未接通。申请成功只表示登记，处理结束不代表退款到账或补发完成；支付仍为商城模拟支付。 |
| 投诉安抚 Agent | 接住投诉和负面情绪，澄清诉求，并将事实核验或人工处理需求交给对应流程。 | 不因情绪承诺赔偿、退款或改变订单状态。人工队列未接通时明确说明，不能声称已转接或已有人接手。 |
| 人工交接 | 将用户、客服助手和人工队列之间的未解决事项形成可跟进的案件。 | 创建案件前向用户展示将共享的摘要/对话内容。摘要分列用户诉求、已核验事实及其来源、已执行动作及证据、仍待处理事项。创建成功只表示工单已创建，不表示人工已经接手或问题已解决。 |

### Agent 执行约束

- 每轮由一个入口路由和至多一个专属 Agent 处理；Agent 之间不开放无界的相互委派或自主循环。
- FAQ、状态查询、取消确认、人工交接等固定流程仍由确定性模块负责；模型负责自然语言理解、澄清和答复表达，不持有买家身份或直接写数据库。
- 所有工具从当前服务端会话派生身份，使用窄参数 Schema 与最小字段返回。商品、政策、订单和外部检索文本始终是数据，不能改写角色、路由和工具权限。
- 订单取消继续使用已实现的明确选择、方案、用户按钮确认、原子执行和结果核验；增加其他写工具不能降低这一门槛。
- 现有模型默认关闭真实外部 exchange。路由/Agent 的合成评测通过后，真实模型调用仍须依据项目既有预算和授权机制单独启用。

## 通用能力

### 知识与商品资料

- 分开维护商城确认的 FAQ、商品结构化属性、售后规则和活动规则，并保存来源、版本、生效区间及适用条件。
- 当前“商品描述”和合成客服政策不能替代真实材质/成分/尺码表、优惠/赠品规则或商城批准的售后政策。
- 知识检索只用于定位候选依据；回答前按商城维护的有效登记核对版本和来源。无匹配、冲突或检索不可用时明确澄清/降级，不用通用常识代替商城承诺。

### 会话记忆

- 短期记忆服务于当前咨询并遵守既有会话期限；切换商城账号、退出或会话失效后，旧身份下的订单上下文立即不可用。
- 长期偏好记忆应是用户可查看、修改、删除和选择退出的独立数据。肤质、身体测量等建议先按敏感偏好处理，不在没有明确用途及保留规则时持久保存。
- 人工工单为解决个案可在独立期限内保存用户授权提供的对话片段/摘要；不把客服页面原始聊天自动写入通用应用日志。

### 工具、审计和指标

- 订单、商品、地址、支付和取消继续通过商城受控接口。承运商、退款、优惠券、发票和通知分别提供独立 Adapter；没有正式配置的能力返回未开通，不伪造成功。
- 区分业务证据、人工工单内容和运行诊断日志。业务操作记录操作者、目标、动作、结果及可核验来源；诊断日志延续字段白名单，不记录秘密、完整邮箱、电话、地址、原始支付凭证或未裁剪自由文本。
- 数据看板先从可审计事件计算路由分布、用户纠正率、工单创建率、工具成功/失败率、检索命中与有效引用率、答后满意度。清晰定义样本、分母和反馈来源，不把“模型回答了”记作解决。
- 保存期限、删除失败行为、用户告知以及工单与审计事件的保留关系须在持久化完整对话前定义。现有客服安全日志不是保存对话记录的方案。

### 多平台接入

淘宝、京东、抖音和拼多多接入属于后续独立平台 Adapter：每个平台有自己的授权、订单/商品 ID 映射、事件签名、限流及数据处理规则。统一后台不能用共享账号密码、爬取或任意 HTTP 工具模拟接入。当前仓库没有这些平台凭据/端点，也没有对应接入，因此不是第一阶段的演示功能。

1. **商城会话集成**（已完成）：商城联系入口在商城站点打开集成客服；客服从商城现有会话显示“已登录/请登录”；按全体有效买家会话查询本人订单。独立 `18011` 隔离演示保持现状。
2. **可用能力的 Agent 化**（已完成）：七类路由、纠正/低置信路径及情绪场景以确定性状态机实现；售前、订单、售后角色可独立评测；固定流程仍由确定性工作流执行；模型路径只在显式注入离线 transport 时参与，默认关闭真实调用。
3. **商品属性与真实运营规则**（部分完成）：知识条目、结构化商品属性发布、检索和冲突检测已实现；推荐条件续接、显式单位尺寸收集、尺码表范围核对及肤质/肤色依据过滤已实现。真实商品资料与运营规则仍需运营方录入。
4. **人工工单**（已完成）：工单状态、人工工作台、摘要、历史授权共享、接手反馈与 30 天保留已实现；自动转人工节点已启用。
5. **售后与外部业务 Adapter**（部分完成）：售后/订单类服务申请的登记、幂等与人工审核已实现，地址修改为唯一受控自动应用路径；退款打款、优惠券、发票、真实物流的外部 Adapter 仍未接入。
6. **指标与多渠道**（部分完成）：服务事件与指标看板（含分子分母与口径定义）已实现；渠道登记已实现，外部平台 Adapter 未接入。

每个阶段分别记录规格、实施和运行验收；某 Agent 的独立评测通过不等于该业务已经有可调用系统接口。

## 设计问题

- 第一阶段的集成目标建议限定为当前本机商城及其合成买家/订单数据；不接生产商城或外部消费者资料。
- 人工交接建议先做商城后台中的本机工单列表，而不是假定已存在某家外部客服平台。
- 当某种业务能力尚无系统接口时，建议返回“暂不支持/需要人工处理”并按规则创建工单；不生成虚构的退款、物流或发票状态。
- 要持久化完整人工上下文时，需让用户知道具体会发送哪些记录、交给谁以及保留多久；运行日志不承担聊天档案职责。

商城会话集成、六职责 Agent 平台、人工工单、服务申请、知识库、偏好记忆、服务通知与指标看板已在本机实施；退款打款、真实物流、优惠券与外部平台接入仍按后续阶段处理。页面合成验证与本机运行验证分别记录，不能相互替代。

## 多轮咨询与服务进度增量（2026-10-25）

结合 [20 份公开资料研究](customer-service-agent-reference-study.md) 补齐现有流程；小红书未取得可核对的笔记全文，不计入这 20 份，也未将外部文章作为商城运营政策。

- 入口：不确定问题先查询当前有效 FAQ；没有依据时才继续澄清或转人工。识别“没有生气”等否定表达；每次工具调用均校验当前角色的工具白名单。
- 售前：保留推荐商品与预算的多轮条件，当前明确预算覆盖已保存预算；肤质和肤色只按已发布的适用属性筛选，没有证据时说明缺资料。比较支持“甲和乙哪个好”等表达。尺码在选择商品后分轮收集显式单位尺寸，支持斤换算公斤，换商品清除旧尺寸；管理台和后端统一严格校验尺码表，页面提供尺寸表单，测量值不写入长期偏好。
- 进度：新增受控只读 `get_service_progress` 与 HTTP 查询入口，返回本人明确选择的订单相关工单（最多十条）、状态、最近人工回复和执行证据。查询不创建申请；选择超过十分钟、咨询或身份失效时拒绝旧授权。工单 `resolved` 不代表业务已执行，退款、开票和补发均显示 `not_connected`，只有同订单的已存地址修改证据可核验为 `verified`。
