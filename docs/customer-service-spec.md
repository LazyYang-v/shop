## Problem Statement

> 历史规格：保留当轮需求与授权边界。2026-10-24 用户已批准[客服作品集发布范围与 13 项验收](customer-service-portfolio-release.md)：虚构数据、合成演示政策、私有源码与本机隔离演示，#9 按此范围收口。[生产化前置条件](customer-service-real-release-prerequisites.md)已归档，不阻塞当前作品集；下文“真实商城政策/WeKnora 接入”不表示当前已实现或必须补齐。现有权限及冻结参数仍以[运行契约](customer-service-runtime-contract.md)为准，历史 OPEN/未授权/待冻结不作为当前结论。

商城已有商品、买家订单、已保存物流信息及未支付订单取消能力，但当前客服页面仅作本地消息演示。访客和买家无法通过客服获得有据可查的商城政策、本人订单信息，以及可确认、可核验的取消结果。

直接让模型访问业务系统会引入身份混淆、自由文本注入、误选订单、重复执行和结果误报。客服不能成为权限绕过入口；知识检索命中也不能取代商城授权或当前业务事实。

## Solution

建立基于 WeKnora 检索的商城客服助手。访客可咨询经确认的商城政策、查询商品与库存；已登录买家可明确选择自己的订单，查询状态与已保存物流信息，或通过独立确认按钮取消本人尚未超时的未支付订单。

规则问题走受控检索，固定业务查询走确定性流程，复合诉求在同一权限边界内组合工具。模型只能查询和提出方案，不能代替用户确认。执行复用商城既有取消规则，凭据消费、取消及证据同事务提交。响应丢失时按操作编号核验，绝不自动重放取消。

本规格用于发布设计，不授权开始实现客服。尚未核实的 WeKnora 能力和未冻结参数须明确完成前置工作，不能默认为已支持或已确认。

## User Stories

1. 作为访客，我希望从首页“联系客服”入口进入客服页面，以便直接咨询购物问题。
2. 作为手机用户，我希望客服页适配屏幕和输入操作，以便在手机上完成咨询和确认。
3. 作为访客，我希望查询商城已确认的政策，以便按本商城实际规则购物。
4. 作为访客，我希望答案提供政策来源、版本和生效依据，以便核对答复。
5. 作为访客，我希望没有明确政策时得到明确说明，以免把通用电商常识误当成承诺。
6. 作为访客，我希望分别获知无匹配、政策冲突和检索不可用，以便理解未获得答案的原因。
7. 作为访客，我希望查询商品、价格与可售库存，以便选择商品。
8. 作为访客，我希望订单问题引导我登录且不泄露订单，以便保护买家隐私。
9. 作为买家，我希望客服绑定当前登录身份，以便只能处理我自己的订单。
10. 作为买家，我希望输入订单号只作为本人订单的查询条件，以免订单号成为越权凭据。
11. 作为买家，我希望不存在与不可访问订单使用一致提示，以免暴露他人订单是否存在。
12. 作为买家，我希望候选卡展示订单号、创建时间、商品摘要、金额和状态，以便选对订单。
13. 作为买家，我希望候选卡不展示地址和电话，以便减少聊天中的个人信息暴露。
14. 作为买家，我希望即使只有一单也由我明确选择，以免客服误解我的操作对象。
15. 作为买家，我希望看到订单当前状态和查询时间，以便理解结果的时效性。
16. 作为买家，我希望查询已保存物流公司、运单号和发货时间，以便掌握商城实际记录。
17. 作为买家，我希望客服明确没有实时轨迹或预计送达能力，以免被虚构物流进度误导。
18. 作为买家，我希望面对退款等不支持的诉求时收到真实能力说明，以免误认为已办理。
19. 作为买家，我希望取消前看到订单号、状态及恢复库存、不可撤销、不恢复购物车的后果，以便作出明确决定。
20. 作为买家，我希望提出取消方案不改变订单，以便咨询与执行分离。
21. 作为买家，我希望只有点击明确的确认按钮才执行取消，以免普通聊天表达被当成授权。
22. 作为买家，我希望确认按钮直接请求商城后端，以免模型替我确认。
23. 作为买家，我希望确认只适用于当前会话、当前方案和当前订单，以免凭据被跨对象复用。
24. 作为买家，我希望订单状态变化或支付超时后拒绝旧确认，以免取消不该取消的订单。
25. 作为买家，我希望重复点击只提交一次业务变更，以免重复恢复库存。
26. 作为买家，我希望退出、身份失效或切换账号后旧授权失效，以便保护订单。
27. 作为买家，我希望收到明确回滚响应后能自行重新确认，以便恢复临时失败且不被自动执行。
28. 作为买家，我希望响应丢失时核验结果而不重复取消，以免产生无法预料的操作。
29. 作为买家，我希望迟到的旧请求在核验撤销确认后被拒绝，以免核验后又发生取消。
30. 作为买家，我希望处理中、已拒绝、已失效、无法核验有明确区分，以便知道下一步。
31. 作为买家，我希望五分钟无法核验后保留操作编号并能手动检查，以便后续确认结果。
32. 作为买家，我希望客服区分超时关闭、当前已取消和本次取消成功，以免错误归因。
33. 作为买家，我希望有效刷新交接撤销旧确认卡，以免旧页面授权继续使用。
34. 作为多标签页用户，我希望普通新标签页不会撤销其他活跃页面，以便独立咨询。
35. 作为买家，我希望交接失败时如实说明短期过期机制，以免依赖无法保证的即时撤销。
36. 作为商城维护者，我希望政策登记由商城掌握，以便旧索引结果不能恢复失效政策。
37. 作为商城维护者，我希望外部研究资料与商城政策隔离，以免文章内容成为业务承诺。
38. 作为商城维护者，我希望商品文案和检索文本只能作为数据，以免注入改变权限或调用流程。
39. 作为商城维护者，我希望令牌、确认凭据和个人信息不进入模型或日志，以便控制泄露面。
40. 作为商城维护者，我希望服务崩溃时取消、库存与执行证据保持一致，以便可靠恢复。
41. 作为商城维护者，我希望无人处理的到期方案自动失效，以免记录永久待确认。
42. 作为商城维护者，我希望页面实例数量和查询频率受限，以免无限增长或订单号探测。
43. 作为评估者，我希望每项能力标明实现与验证状态，以便区分事实、设计和假设。
44. 作为评估者，我希望黄金、边界、回归、安全场景有固定预期和实际结果，以便衡量完成情况而非依赖未经测量的指标。

## Implementation Decisions

### 范围与身份

- 调用链为浏览器、商城客服后端、受控 MCP 工具。业务身份仅取服务端校验过的认证会话，不接受模型或用户指定 user_id、buyer_id、邮箱、手机号作为授权。未登录仅允许政策及商品库存查询。
- 复用现有会话、买家归属、CSRF 和来源校验，不增加管理员代查、业务特权、数据库直连、任意 URL/SQL 或通用工具透传。
- 退出、会话失效及切换账号后，每次订单请求重新鉴权；不缓存授权结果。
- 不增加新的订单业务动作。浏览器确认和结果核验是受保护的协议接口，后者可以撤销授权记录，但不直接修改订单。

### 六个模型工具与数据边界

- 政策检索：输入问题与可选政策类别，输出有效条目、来源、版本、生效区间或受控失败。
- 商品列表：输入关键词、分类、分页，输出当前商品摘要、价格、库存及上下架状态。
- 商品详情：输入商品标识，输出当前商品信息。
- 本人订单列表：输入状态、分页、可选订单号过滤，输出裁剪后的本人候选摘要。
- 本人订单详情：输入订单标识，输出状态、商品摘要、金额、支付截止、关闭原因和已保存物流信息，不返回地址电话。
- 提出取消方案：输入已由用户明确选定的订单，创建操作记录并产生确认卡；不修改订单。模型仅获得摘要与操作编号，凭据经独立前端通道下发。
- 统一输出请求标识、查询时间、结果状态、可展示数据；拒绝未知输入字段。空结果、无政策、冲突、不可用与权限错误不得混为一谈；不返回内部堆栈。
- 商品名称、描述、政策原文等工具结果一律为数据，不得作为行为指令。确认执行和结果核验不注册给模型。只允许已核实的外部检索工具，独立强制白名单。

### 政策与 WeKnora

- RAG 采用 WeKnora。商城维护政策标识、来源、版本、生效区间和状态的权威登记；WeKnora 仅作检索索引。
- 发布时检查有效区间冲突，检索后核对权威登记。失效版本及过期历史引用不能作为当前依据；冲突时停止政策结论并记录问题。无规则不以常识补全。
- 当前订单、库存、物流和金额以业务 API 为准。检索失败不阻断独立订单查询。
- 外部文章仅进入标注为非商城政策的研究资料，不进入政策索引。
- WeKnora 令牌仅服务端保存，不进入前端、模型、日志或工具返回。部署端点存在不证明权限或能力。
- 必须实际核实：部署版本和 MCP 传输及工具 Schema；版本过滤与生效区间；结果来源及版本元数据；索引更新/删除及旧条目残留；工具白名单；令牌权限、知识库隔离和撤销；超时；限流；不可用及鉴权/参数错误形态；混合检索与 Rerank 配置。
- 每项记录实际调用时间、部署版本和脱敏证据，或准确官方文档链接。能力不足时补充商城侧校验并验证，无法可靠映射来源或隔离权限时明确阻塞接入。当前这些能力均待实际核实。

### 选择与确认凭据

- 零、一、多订单都由买家明确选择，不以最近一单或唯一一单代替选择。订单号过滤仅在本人范围，不存在和他人订单统一未找到可访问订单，并限制探测频率。
- 方案展示订单号、当前状态、取消后果；生成不可猜测操作编号和随机一次性确认凭据。
- 凭据绑定买家、认证会话、咨询会话、页面实例、订单和取消动作；有效期取签发后两分钟与订单支付截止中的较早者。
- 服务端仅存凭据哈希，明文只在签发响应返回浏览器内存，通过确认正文提交，不进入模型、聊天、URL、日志或浏览器持久存储。操作编号不能替代权限校验。
- 确认请求携带操作编号和凭据，订单及动作取自服务端记录，不接受客户端替换。自然语言“好的”等不执行写操作。

### 事务、状态与证据

- 操作记录持久状态仅为待确认、已执行、已拒绝、已失效；从待确认单向转入终态。不提前提交执行中状态。
- 调用方管理事务。现有取消领域逻辑需调整为由调用方提交，原取消 API 与客服执行路径共用校验和关单逻辑，不另写绕过路径。
- 同事务中锁操作记录、原子消费凭据、锁订单、核对身份归属/待支付/未超时、取消恢复库存、写本次执行证据。凭据以条件更新或唯一约束保证一次性，不能靠先查后写。
- 业务拒绝的状态、原因和证据同事务提交，凭据作废。临时故障确定回滚则所有写入撤销，凭据未消费，有效期内可由用户再次点击。
- 提交后独立读取订单展示，查询不承担授权；只有执行证据与最终状态一致才说本次成功。现有关闭原因可区分买家取消与支付超时，不需新增该字段。
- 明确回滚响应不得自动触发核验。进程中断、连接超时、响应丢失一律结果未知，不能推断回滚。取消执行永不自动重试。

### 结果核验与清理

- 仅无明确响应时自动核验；提供手动重新检查入口。核验需认证会话、CSRF、来源及操作归属校验，不给模型调用。
- 核验获取与执行相同的操作记录排他锁，最多等一秒；取不到返回处理中，不能读旧记录断言回滚。
- 已执行/已拒绝返回证据；已失效返回同一结果；仍待确认则以条件更新置已失效并撤销旧凭据，提交后说明未发现已提交执行且旧确认已撤销。后续迟到执行拒绝，不取消订单。
- 核验幂等，前端从结果未知起按二、四、八秒退避，其后每十五秒，加入少量抖动，总窗口五分钟；确定结果或身份失效立即停止。超时显示无法核验并保留操作编号，引导查看订单，不声称转人工。
- 浏览器核验状态独立于业务记录，不覆盖真实证据。直接查到关闭仅证明当前状态，不能证明由本次客服执行。
- 无人再次确认/核验的待确认记录在到期后后台条件失效。入口即时校验期限，不依赖扫描授权；清理不得覆盖其他终态，重启后恢复任务。
- 普通只读临时网络/服务错误最多重试一次；鉴权、权限、参数错误不重试。结果核验的有限幂等重试与取消不重试分别处理。

### 页面交接

- 服务端生成页面实例并绑定认证会话；普通不同标签页独立。实例标识不入模型、URL、日志或持久存储。
- 唯一持久存储例外是 sessionStorage 中的随机交接标识，仅识别刷新前驱，不能查询订单、签发确认或执行取消，也不能替代登录、CSRF 或凭据。
- 交接标识九十秒有效，活跃页面每三十秒续期，同页只允许一个续期在途；页面恢复立即尝试续期。续期条件匹配当前会话/实例且有效未消费，只延长有效期，不能复活已消费标识。
- 完成交接才一次性消费并轮换标识、撤销前驱未执行凭据。复制标签页冲突可保守使旧卡失效，不保证完全互不影响。
- 过期、丢失、会话不匹配或交接失败只新建实例，不凭无效标识撤销他人实例；无法交接不承诺即时撤销，关闭标签页同样无可靠撤销事件，由凭据期限和会话校验兜底。
- 交接续期不延长确认凭据有效期；页面实例需有数量上限并清理过期实例。

### 未冻结事项与完成条件

- 以下不是已确认数值：每会话实例上限及清理周期、限流阈值、消息/分页/工具调用上限、记录保留期限、模型提供方与编排框架。十个实例和三十秒清理仅为既有建议，不作为验收硬值。
- 精确 HTTP 路由、状态码、错误码和最终工具 Schema 亦待实现前冻结。既有已确认期限与安全边界不得因此弱化。
- 默认不强制使用 LangGraph/ReAct，不接受未经测量的成本比或自助解决率。首版以可测业务闭环验收。

## Testing Decisions

- 测试只验证外部行为，不断言私有方法、SQL 形态或内部调用顺序；优先现有最高边界。既有访谈已确认浏览器/商城 API 及超时扫描入口，本规格沿用，不新增未经讨论的测试层。
- 浏览器到商城 API 的用户流程是主要验收边界：入口、登录、选订单、提出方案、按钮确认、最终证据和移动布局。后端 API 集成测试沿用真实隔离 PostgreSQL 和现有认证、归属、CSRF 测试惯例，验证并发及事务故障。后台到期清理通过现有扫描入口模式验证。
- 外部 WeKnora 单独做边界契约核实，用已批准测试知识库/令牌和低量请求保存脱敏证据；不通过模拟返回证明真实平台支持。
- 正常场景：政策有据、商品库存一致、本人订单和物流一致、取消闭环证据可查；所有关键答复能够对应规则条目或 API 结果。
- 授权与注入：未登录、跨买家订单/操作、账号切换、失效会话、错误来源、缺 CSRF、篡改绑定、未批准工具、商品及政策恶意指令全部验证，禁止个人信息和秘密泄露。
- 确认：零/一/多单必须明确选择；提出方案不改订单；聊天同意不执行；模型不具有执行能力；超时、旧页面、旧动作和重复点击无越权变更。
- 原子性：业务写入和证据故障一起回滚；双击仅一次提交；提交前后进程/连接故障不产生部分业务结果；原取消 API 行为保持兼容。
