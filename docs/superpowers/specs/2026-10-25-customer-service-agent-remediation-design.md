## 目标与证据边界

先修复服务申请幂等和工单聊天来源两项 P2 问题，再在**新的、固定的提交**上验收真实 DeepSeek 六工具调用、WeKnora 实时检索和 Agent 专项评测。`941fe4e` 的 13 项历史作品集结论及其 399/28 项旧测试记录保持版本绑定；新功能不得沿用该结论。当前本机业务流程、商城会话、订单归属、显式选单、取消确认和结果核验继续是权限与事实边界。

本规格针对隔离、虚构数据的新版作品集候选。真实买家数据、真实商城政策发布、生产 WeKnora/模型账号与保留契约仍按[生产化前置条件](../../customer-service-real-release-prerequisites.md)另行批准；新版作品集的 live 测试也必须先确定专用资源、凭据交接、请求与金额上限。本文件不授予付费调用、知识库写入、数据库重置或部署权限。

## 阶段 1：两项 P2 修复

### A04-1 服务申请幂等指纹

现状：`customer_service_support.py:create_case` 只比对同一买家的请求键、申请类型和订单 ID；`customer_service_support_api.py:support_request` 在检查当前选单与地址后才调用它。因而同键修改诉求、发票抬头、地址或共享选择可能返回旧申请；成功后的迟到重试也可能先被已过期选单挡住。

**输入语义**：仅人工提交的 `request:<client_request_id>` 使用内容指纹；自动转人工的 `auto:<consultation.id>` 继续“一次咨询一单”，后续重复转人工返回原单，不因后续话术不同而冲突。人工请求的规范化命令包含 schema 版本、买家 ID、请求 UUID、申请类型、选定订单 ID、页面与咨询 ID、诉求、地址 ID、发票抬头、`share_history` 和确认位。UUID 用标准小写形式；自由文本仅做 Unicode NFC 与首尾空白规整，不折叠内部文字、不改变存入工单的原文。以稳定排序和 UTF-8 编码序列化后计算 SHA-256；日志和响应不得输出原文或指纹所含的私人字段。

**处理顺序**：先验证当前买家身份、Origin/CSRF 和输入形态，再按买家 ID + 请求键查找已存在申请。若存在且指纹相同，返回原工单，不再次检查已经失效的页面选单或当前地址快照，也不追加第二条创建事件；若指纹不同，返回 `409 Conflict`，说明该请求编号已用于不同内容。若不存在，走现有咨询、显式选单、本人订单和地址检查，固定第一次提交时的地址快照、内容指纹与工单，单事务提交。保存的地址后来变化不改写原申请；同键同命令仍返回原快照，使用新的地址意图必须换新请求编号。

**并发与迁移**：保留数据库的 `(buyer_id, request_key)` 唯一约束。跨会话同买家同时提交时，只允许一个插入和一条创建事件；竞争者读回获胜行后按指纹返回原单或 409，数据库唯一冲突不能外泄为 500。下一迁移（预计 `0023`，实际编号以实施时 migration head 为准）新增可空的 `request_fingerprint` 字段；既有 `request:` 工单因缺少原始请求内容无法安全回填，重放该旧键时返回明确 409，原工单仍可查看/回复。`auto:` 工单无需指纹。过期工单按现有 30 天清理，过期后的旧键不承诺继续去重。

**验收用例**：首次创建与逐字节重试；仅首尾空白/NFC 差异；诉求、发票抬头、地址 ID、共享选择、订单或咨询 ID 改动；原地址记录在首次创建后发生修改；选单过期后重试；双会话同买家并发同内容/不同内容；API 进程重启后重试；匿名、他人买家、CSRF 缺失及非法额外字段。核对工单数、创建事件数、响应状态和旧申请详情。

### A04-2 工单聊天来源绑定

现状：`share_context` 验证工单买家和咨询所属会话，却没有验证该工单来源于传入咨询。`SupportCase` 也没有来源咨询字段。

每个新工单记录 `source_consultation_id`：人工申请来自已验证的 `payload.consultation_id`，自动转人工来自当前 `consultation.id`。创建时必须证实咨询及页面属于当前认证会话、当前会话买家与工单买家相同。`Consultation` 自身只有 `session_id`，没有 `buyer_id`；不能按不存在的 `consultation.buyer_id` 设计校验。咨询最多保留约 24 小时而工单保留 30 天，因此字段保存来源 UUID，不建立会在咨询清理时抹掉来源的级联外键。只在咨询仍有效时允许新增共享片段。

`POST /api/customer-service/cases/{case_id}/share-context` 保持现有请求形态和买家明确 `consent: true`。服务端要求工单属于当前买家、咨询属于当前认证会话、咨询未过期，且 `case.source_consultation_id == payload.consultation_id`；失败不修改工单。共享内容只取该来源咨询已经脱敏的必要片段，最多保留现有 12 条上限，重复调用不得扩大范围或重复追加。旧工单的来源字段为 `NULL`，无法可靠推断来源；保持查看、回复和审核能力，但拒绝新增聊天共享并给出明确状态，不自动把同会话其他咨询绑定为来源。跨咨询共享若未来需要，应另设显式授权和独立审计，当前不开放。

**验收用例**：人工申请与自动转人工都写入来源；同来源且明确同意可共享；同买家同会话的另一咨询、另一会话、另一买家、过期咨询、遗留空来源、缺少同意分别被拒绝；共享只含允许的脱敏片段，重复请求不增量扩展；咨询清理后来源 UUID 仍留在工单中供审计。

## 阶段 2：受控真实 Agent Runtime

现有 `run_specialist` 调用 `classify` 后走确定性流程；`plan_with_model` 是未接产品入口的受控离线规划边界。旧六工具 `CompositeTools.run_model` 可经构造器注入合成 exchange，但应用默认没有真实 transport，且对六工具路径显式拒绝 `_https_exchange`。实施时先盘点并复用 `CompletionTransport`、预算账本、已验证工具结果和交付前身份复核，不为框架名称重写业务。

新增专用、默认关闭的 live 能力开关与服务端配置。启用前固定提供方/API 与模型版本、专用演示账号、令牌来源、价格卡、请求数/金额上限、并发与截止时间、允许发送的合成字段、失败停止条件及批准记录；不通过浏览器参数或普通用户文本开启。真实 exchange 必须经过现有付费预留、额度和超时守卫，迟到或不确定结果不得自动重发。模型只看裁剪后的引用代号与经核验事实；服务端根据会话、角色、显式选单和每轮预算重建允许工具列表并校验每次调用。取消仍只能提出方案，确认及核验不注册给模型；服务申请仍走独立买家确认接口。每轮至多一个专属角色，固定业务流程可维持确定性；失败时明确 partial/澄清/人工路径，不声称模型已完成未执行动作。

在专用合成环境至少实测单工具、多工具组合、工具失败后三类任务；分别保存准确源码/镜像、模型版本、脱敏请求 ID、工具顺序、预期/实际、usage 与金额、失败和回退证据。旧 #3 的商品真实兼容性 6 次请求不得当作新版六工具通过。若现有编排能满足边界，不引入 LangGraph。

## 阶段 3：WeKnora 只读检索

先固定专用 WeKnora 版本、真实协议/Schema、KB 范围、只读凭据和故障注入资源，再实现独立 Adapter。现有进程内合成索引与商城本地词法知识继续作为各自明确标注的路径，不能在指标或界面中冒称 WeKnora。Adapter 仅返回候选引用；商城权威登记按知识库/文档 ID、来源、正文哈希、版本、状态、UTC 有效期及适用范围重验后才可引用。越范围、撤回、版本冲突、无匹配、超时和服务故障分别给出可辨状态；检索内容及提示词注入不能扩大角色、工具或买家权限。真实调用限于批准的专用资源；共享知识库不因本规格获得写入、删除权限。

验收同时覆盖正向引用、跨 KB 负向访问、旧版本/撤回/冲突、返回文本注入、检索故障时独立订单查询、依赖恢复及日志最小化。缓存/索引零命中不证明备份删除。

## 阶段 4：新版验收与发布

先冻结新的源码 SHA、镜像 digest、配置摘要及测试数据版本，再冻结与实现用例分开的 Agent Eval 集：多轮改口、单/多工具、知识冲突、越权、注入、超时、人工恢复和结果核验。每例记录输入、允许/禁止动作、预期、实际、脱敏 trace、工具与引用证据；安全关键例要求零越权和零未授权写入，质量通过阈值由项目负责人在 live 测试前批准，不能见结果后移动门槛。后端真实隔离 PostgreSQL、桌面/移动 Chrome、受控真实模型与专用 WeKnora 分层报告，不把合成、Mock、真实调用计数相加。保留失败、费用、部署/回退和已知限制。只有准确新版候选达到冻结门槛后，README 才能将相关能力从“开发中”改为“已验收”；旧 `941fe4e` 结论保持原样。
