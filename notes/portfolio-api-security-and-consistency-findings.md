# Portfolio API security, testing, and transaction findings

Scope: one FastAPI API, a TypeScript SPA, and PostgreSQL. The recommendations below assume the SPA and API can be served from the same site (ideally same origin); if deployed on distinct sites, cookie and CORS behavior requires additional care.

## Authentication and browser sessions

**Recommendation: use an opaque server-side session ID in a cookie for this single first-party SPA/API.** The server can revoke a session immediately and keep role or account state centrally; OWASP recommends session identifiers be meaningless, unpredictable, and generated with a CSPRNG, with session meaning stored server-side. Use a host-only cookie with `Secure`, `HttpOnly`, and `SameSite=Lax` (or `Strict` if the navigation behavior allows it), narrow `Path`, and no `Domain`; rotate the identifier after login and privilege changes, and expire/invalidate it on logout. OWASP documents these cookie attributes, session lifecycle, and session ID renewal requirements. ([OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html))

JWT bearer tokens are useful when independently deployed services need portable claims or token-based API clients are a real requirement. They add signing-key management, expiration/revocation complexity, and claim freshness considerations; JWT payloads are encoded, not encrypted, so do not put secrets in them. FastAPI's OAuth2/JWT tutorial demonstrates signed JWTs, expiration and password hashing, but does not make JWT the default choice for a first-party browser SPA. ([FastAPI OAuth2 with Password and Bearer JWT](https://fastapi.tiangolo.com/tutorial/security/oauth2-jwt/))

**CSRF:** cookie authentication is attached automatically by browsers, so protect every state-changing request. Use a synchronizer token tied to the session (or a correctly implemented double-submit pattern), send it in a custom request header from the SPA, and validate it server-side; also validate `Origin`/`Referer` where appropriate. `SameSite` is defense in depth, not the sole control, especially where subdomains or cross-site flows are involved. ([OWASP CSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html), [OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html))

**Passwords:** store only salted adaptive password hashes, never plaintext or reversible encryption. Prefer Argon2id with a maintained password-hashing library and parameters tuned to the deployment; FastAPI's current tutorial uses `pwdlib` with Argon2, and OWASP's password storage guidance specifies Argon2id as the preferred general-purpose choice. Rehash on successful login when parameters have become outdated. ([FastAPI OAuth2 with Password and Bearer JWT](https://fastapi.tiangolo.com/tutorial/security/oauth2-jwt/), [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html))

**Authorization:** enforce authorization on the server for every request and every object/action. Derive the principal from the validated session; scope database reads/writes to the caller's ownership or permitted role, and deny by default. Hiding UI controls is not an authorization boundary. FastAPI dependency-based security can resolve the current user and scopes, while OWASP emphasizes per-request checks and object-level access controls. ([FastAPI OAuth2 scopes](https://fastapi.tiangolo.com/advanced/security/oauth2-scopes/), [OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html))

## Testing layers and tools

- **Unit tests:** pytest for pure domain rules and service behavior (state transitions, validation, fee/total calculations). Keep these fast and avoid HTTP/database setup where not needed. pytest's fixtures and parametrization support reusable setup and broad edge-case matrices. ([pytest fixtures](https://docs.pytest.org/en/stable/how-to/fixtures.html), [pytest parametrization](https://docs.pytest.org/en/stable/how-to/parametrize.html))
- **API tests:** exercise FastAPI routes through HTTPX `ASGITransport` (with lifespan handling as required), asserting response shape, authentication, CSRF, authorization, and error cases. These tests cross the routing/dependency boundary without a real network listener. ([HTTPX transports](https://www.python-httpx.org/advanced/transports/), [FastAPI async tests](https://fastapi.tiangolo.com/advanced/async-tests/))
- **Database integration tests:** run migrations and transaction/repository tests against real PostgreSQL, not SQLite, because locking and isolation behavior are database-specific. Testcontainers' PostgreSQL module starts a disposable PostgreSQL container, suitable for CI when Docker is available. ([Testcontainers Python PostgreSQL](https://testcontainers-python.readthedocs.io/en/latest/modules/postgres/README.html), [PostgreSQL explicit locking](https://www.postgresql.org/docs/current/explicit-locking.html))
- **Browser end-to-end tests:** Playwright for representative SPA journeys: login, CSRF-protected mutation, order placement, cancellation, and user-visible outcomes. Use a small deterministic set of browser tests and a real API/database environment; Playwright's official docs cover browser projects, fixtures, and end-to-end practices. ([Playwright browser projects](https://playwright.dev/docs/test-projects), [Playwright best practices](https://playwright.dev/docs/best-practices))

## Order, payment, cancel, and timeout consistency

Treat the database as the authority for order state. Model explicit legal transitions (for example `pending_payment → paid`, `pending_payment → cancelled`, and `pending_payment → expired`), with constraints against contradictory terminal states. Perform each transition in a short database transaction and commit before calling an external payment provider; do not hold row locks across network calls. SQLAlchemy's `Session` provides transaction framing and explicit commit/rollback; PostgreSQL transactions make the set of database changes atomic. ([SQLAlchemy Session transactions](https://docs.sqlalchemy.org/en/20/orm/session_transaction.html), [PostgreSQL transactions](https://www.postgresql.org/docs/current/tutorial-transactions.html))

For competing placement/cancel/timeout/payment callback operations, serialize changes to the same order by selecting its row `FOR UPDATE` inside the transaction, re-reading its current state after acquiring the lock, and allowing only a valid transition. SQLAlchemy exposes this via `with_for_update()`; PostgreSQL row locks block conflicting updates/locks until the transaction ends. Keep a consistent lock order when multiple rows are involved to reduce deadlocks, and retry transactions aborted for serialization failures/deadlocks where appropriate. ([SQLAlchemy `with_for_update`](https://docs.sqlalchemy.org/en/20/orm/queryguide/query.html#sqlalchemy.orm.Query.with_for_update), [PostgreSQL explicit locking](https://www.postgresql.org/docs/current/explicit-locking.html), [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html))

Use database constraints as the final backstop: unique idempotency keys for client order placement and provider event IDs for payment callbacks; unique constraints are enforced under concurrency. A duplicate request/event should resolve to the already-created result rather than create a second order or apply a payment twice. PostgreSQL `INSERT ... ON CONFLICT` provides an atomic insert-or-update outcome under concurrency for the specified unique/exclusion constraint. ([PostgreSQL `INSERT`](https://www.postgresql.org/docs/current/sql-insert.html), [PostgreSQL constraints](https://www.postgresql.org/docs/current/ddl-constraints.html))

External payment cannot be made atomic with a PostgreSQL transaction. Persist the order and an outbox/job record atomically, then have a worker call the provider with an idempotency key and record the outcome; reconcile ambiguous timeouts by querying/retrying the provider idempotently. Treat provider webhooks as at-least-once: verify their authenticity, deduplicate by provider event ID, and lock/update the order transactionally. The outbox is an application design inference from the database's transaction boundary and provider idempotency behavior, not a FastAPI or PostgreSQL feature. ([PostgreSQL transactions](https://www.postgresql.org/docs/current/tutorial-transactions.html), [OWASP Web Service Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Web_Service_Security_Cheat_Sheet.html))

An expiration worker should select eligible pending orders, then lock and transition each order in a transaction only if it remains pending and its deadline has passed. `FOR UPDATE SKIP LOCKED` can let multiple workers claim distinct rows, but PostgreSQL documents it as an inconsistent view suited to queue-like consumers, not general reads. ([PostgreSQL `SELECT` locking clause](https://www.postgresql.org/docs/current/sql-select.html), [SQLAlchemy `with_for_update`](https://docs.sqlalchemy.org/en/20/orm/queryguide/query.html#sqlalchemy.orm.Query.with_for_update))

Add race-focused integration tests that run cancel, timeout, duplicate placement, and duplicate/late payment notifications concurrently against PostgreSQL; assert exactly one legal terminal outcome, one effective charge/order, and a consistent audit trail. Unit/API tests alone cannot establish PostgreSQL locking semantics. ([PostgreSQL explicit locking](https://www.postgresql.org/docs/current/explicit-locking.html), [Testcontainers Python PostgreSQL](https://testcontainers-python.readthedocs.io/en/latest/modules/postgres/README.html))
